# STEAM × RL Token の新手法（検討と検証）

## 動機（ユーザーの整理）
- STEAM の課題: 計算が重い（私たちの計測: critic 学習 2,000 step 8.3 h、Advantage 計算 62.3 万サンプル ≈ 9.8 h（17.7 サンプル/秒）、Step4 の VLA 学習 1,450 step 16.5 h、いずれも A5000）。
- RL Token の課題: 報酬設計が必要（私たちは「把持が確認されたら +1」を手で設計した。把持の判定は環境側の手作りのゲート）。

## ユーザーの提案
1. 報酬（選抜の基準）として、STEAM の時間オフセットを使う。
2. 時間オフセットの観点で良いデータだけを選び、SFT で学習する（STEAM と同様）。
3. SFT で学習するのは、追加した RL Token の actor だけ（RL Token と同様）。
4. RL Token の critic は削除する（STEAM に合わせる）。

期待する利点:
- 時間オフセットの判断を、重い事前学習なしに、基盤モデルの特徴で行う。
- actor に、出力の信頼度（入力が学習データの範囲にあるか）も出させる。
- 複数タスクでは、タスクごとに actor を作り、信頼度の高い actor を推論時に使う（actor の表現力が高くないため）。

## 検討の結論（2026-10-05、Claude）
成り立つ点: 報酬設計が不要になる。学習するのは約 5 MB の actor だけなので、STEAM の Step4（VLA 全体）より軽い。

懸念（すべて予測。検証が必要）:
- (a) **コピー問題**: actor の入力に VLA の提案 ã が入る。ベース VLA が動かしたデータでは、実行した行動 ≒ ã なので、選抜して SFT しても、「ã をそのまま出す」ことを学ぶだけになる。改善が生まれるのは、実行した行動が ã と違うデータ（actor 自身のノイズ付きロールアウト、人間のデモ・修正、他の方策のデータ）だけ。反復（ノイズ付きで動かす → 選ぶ → SFT）が必要。
- (b) **critic なしのサンプル効率**: critic は、行動を良くする方向の勾配を与える。外すと、ランダム探索に近くなり、同じシミュレーション回数では遅くなる可能性がある。
- (c) **把持の失敗を罰しにくい**: 私たちの最大の失敗は、2 つ目の把持の空振り。直前まで画面は「進んで」見える。時間オフセットが区別できるかは未確認。STEAM の私たちの結果（0.52）は、把持を報酬にした RL Token（0.74）より低い。
- (d) **「事前学習なしで基盤モデル」は難しい**: VLM に 2 枚の画像の前後を聞く方法は、STEAM 論文が批判する点（VLM の事前知識が接地していない）に当たる。現実的なのは、凍結 VLA の RL token（計算済み）を入力に、小さな MLP で時間オフセットを学習する方法（数分）。
- (e) STEAM の重さの正体は、画像 2 枚を毎回 SigLIP + Gemma に通す部分と、VLA 全体の学習。特徴量を再利用すれば、どちらも減る。
- (f) **信頼度**: actor が自分で出す分散（NLL）は、データのノイズであり、「学習データの範囲外か」ではない。アンサンブルのばらつき、または z_rl の近傍距離のほうが確実。z_rl は encoder ごとに違うため、複数タスクで比較するには encoder を共有する必要がある。LIBERO ではタスクは指示文で分かる。信頼度で選ぶ意味があるのは、1 タスク内の局面の切り替え（私たちは手作りの把持ゲートと専用 actor で 0.74）。どの actor も信頼度が低ければ、VLA の ã をそのまま使う、という安全側の動作も可能。

代替案 B（最小の変更）: RL Token の critic は残し、報酬だけを時間オフセットに置き換える（報酬設計の課題と重さを同時に解決）。
時間オフセット ≒ Φ(s_{t+H}) − Φ(s_t)（Φ = エピソードの進み）とみなすと、ポテンシャル型の報酬整形になる。ただし失敗エピソードの罰は別に必要。

## 検証計画
- **E0**: RL token（z_rl、960 次元）から、小さな MLP で時間オフセットを予測できるか。
  - 評価: (1) 未使用エピソードでの bin 精度・順位相関。(2) STEAM の critic（2,000 step）が付けた A_STEAM との順位相関。(3) 成功・失敗エピソードの区別。
  - データ: 既存の特徴量（`tmp/rlt_stage1/feats*`）から、`tmp/hybrid/make_zrl.py` で z_rl を計算（t が 6 の倍数のフレーム）。
- **E1**: Task 0 で、A（critic なし、フィルタ付き SFT、反復）と B（critic あり、報酬をオフセットに置換）を比較。基準: ベース 0.46、最良の H 0.74（success_once、50 エピソード）。
- **E2**: 信頼度（アンサンブル vs 近傍距離）を、別タスクの z_rl に対する検出精度（AUROC）で比較。
- **E3**: 複数タスクでの actor 切り替え（encoder の共有が必要）。

## 前提・資産（確認済み）
- RL token: smolVLA の VLM 最終層の先頭 128 トークン（画像）→ `RLTTokenEncoder`（2 層、8 ヘッド）→ 1 × 960。現在の 1 時刻の観測だけから作る（履歴なし）。コード: `RLinf/rlinf/models/embodiment/modules/rlt_token_transformer.py`、`SmolVLARLTFeatureModel`（パッチ `smolvla-u-rlt-stage2-libero.patch`）。
- Stage 1 の encoder: `tmp/rlt_stage1/rlt_stage1_ckpt.pt`（`net`、`scale`）。
- 特徴量（128 × 960、fp16）: `tmp/rlt_stage1/feats`（t = 40〜100、2 おき）、`feats_rest`（それ以外、6 おき）、`feats_demo*`（デモ）。メタに ep、t、succ、state、gap、cmd。
- STEAM: critic は成功エピソード（デモ + ロールアウトの成功）だけで学習（`data.only_success=true`、k = 32、32 ビン、1 メンバー）。Advantage 計算は固定ペア (t, t+32)。分位数は、ロールアウト上位 30%、デモ上位 80%（STEAM 論文の既定値）。
- RL Token の報酬（H の設定）: 把持確認（指令が「閉じる」で、隙間 0.04〜0.071 が 8 ステップ連続）で +1、1 回だけ。

### E0（2026-10-05）: RL token の特徴量から時間オフセットを予測できるか — 結果: 可能（ただし限定つき）
- 実装: `tmp/hybrid/make_zrl.py`（既存の特徴量から z_rl を計算、約 4,189 エピソード、t が 6 の倍数のフレーム）、`tmp/hybrid/e0_offset.py`（MLP: [z_t, z_u, z_u − z_t] → 正規化オフセット、2 層 512、Huber 損失、15 epoch、約 1 分）、結果 `tmp/hybrid/e0_result.txt`。
- 設定: 成功エピソードだけで学習（STEAM と同様）。オフセットは ±6〜30 フレーム（k = 32 に近い）、エピソード長で正規化（L_max = 成功エピソード長の 95 パーセンタイル）。train/demo は、エピソード単位で 80/20 に分割。eval は別セット（64 エピソード）。
- 結果:
  - 未使用の成功エピソード: 前後の判定の正解率 0.995、真のオフセットとの Spearman 0.989。eval の成功 0.998 / 0.991。
  - eval の**失敗**エピソード: 正解率 0.719、Spearman 0.495（成功より大幅に低い。失敗では、同じ場面が繰り返されて、時間の前後が見た目から分かりにくいため）。
  - STEAM の critic（2,000 step）の A_STEAM との一致（未使用エピソード、STEAM のラベルがあるフレーム 19,519 件）: プール全体の Spearman 0.779、上位 30% のラベルの一致率 0.891（Cohen κ 0.740、IoU 0.692）。ただし、エピソード内の順位相関は、成功エピソードで 0.04（ほぼ 0）、失敗エピソードで 0.557。
  - 成功・失敗の区別（エピソード平均スコアの AUROC）: eval 1.000（24/64 が成功）、未使用の学習データ 0.999（356/825）。
- 解釈と注意:
  - 2 つの指標は、「どのエピソード・どの区間が遅いか」では、よく一致する。成功エピソードの中の細かい順位は、一致しない（A_STEAM 自体、エピソード内では、予測のノイズが大きいことを、以前に確認している）。
  - AUROC がほぼ 1 なのは、失敗エピソードが、すべて上限の 520 ステップまで続く長いエピソード（成功は 230〜300 程度）だからで、長さ正規化により「遅い」＝「失敗」となるためと考えられる。「空振りした局面」を区別できているかは、このテストでは確かめられていない（懸念 (c) は未解決）。
  - 同じ初期状態のエピソードが、学習と評価に分かれている可能性がある（エピソード単位の分割のみ）。数値は楽観的かもしれない。
  - STEAM のラベル表（`tmp/steam/step4/adv_train_merged_n32e2000_endfixD_q30.parquet`）は、マージ済みデータの**先頭 1,458 エピソード**（各 T − 8 フレーム）のみ。マージ済みデータの `episodes.jsonl` の `is_success` は、結果と一致しない（先頭 1,458 件が True）ため、成功の判定には、フレームの `is_success` 列を使うこと。
- 次: E0b（空振り局面の区別: 把持確認のゲートの前後で、スコアが落ちるか）、E1（A と B の比較）。

### E0b（2026-10-05）: 空振りの局面を見分けられるか — 結果: 見分けられる（中程度）
- 把持の指令（閉じる）があるフレームを、空振り（隙間 ≤ 0.03）と保持（隙間 0.04〜0.071）に分け、前向き 30 フレームの時間オフセットのスコアを比較（未使用エピソード + eval、62,599 フレーム）。
- 平均スコア: 空振り 6.62、保持 33.26、開いている 19.98。AUROC（保持 vs 空振り）0.832。
- 成功エピソード内だけ 0.853、失敗エピソード内だけ 0.654（失敗エピソードでは、保持と空振りの差が小さい）。
- 注意: 空振りの前後は「進んでいない」ので、スコアが低いのは自然。把持の確認ゲートの定義（8 ステップ連続）とは、厳密には一致しない（格子の 1 フレームで判定）。懸念 (c) は、「全く見分けられない」ではなかったが、失敗エピソード内では、弱い。
- 結果ファイル: `tmp/hybrid/e0b_result.txt`、フレーム表 `tmp/hybrid/e0b_frames.parquet`。

### E1 の実装（2026-10-05）
- パッチ `patches/rlinf/smolvla-x-offset-sft.patch`（コミット 5cee4e6）。クリーンな RLinf に、他のパッチと順に当てて、開発用コピー（`tmp/rlinf_dev`）と同一になることを確認した。
  - `rlinf/algorithms/rlt/offset_score.py`: MLP（E0 の `tmp/hybrid/offset_mlp.pt`）で RL token の対のオフセットを計算。
  - `fsdp_rlt_ac_policy_worker.py`: `algorithm.rlt_offset.{enable, mode, ckpt, lookahead, top_fraction, sft_weight, reward_scale, reward_mode}`。
    - `mode=sft`（案 A）: 取り込み時に、各チャンクのスコア = f(z_t, z_{t+3}) を `rewards` に保存。actor の損失 = bc_weight × BC(参照) + sft_weight × （バッチのスコア上位 30% の実行チャンクへの MSE）。critic は学習しない（損失 0）。ウォームアップ中は SFT の重み 0（参照への BC のみ）。
    - `mode=reward`（案 B）: 報酬 = reward_scale × f(z_t, z_{t+1}) / L_max で置換（`reward_mode=add` なら、環境の報酬に加算）。最後の遷移は、1 つ前の値を使う。
  - 実行: `tmp/rlt_stage2/run_e1.sh`（`run_stage1_long.sh` の複製。tensorboard のみ、wandb へは送らない）、`run_e1_chain.sh`（A → B）。
- スモークテスト（A、B とも、数エポック）は、エラーなく完走。
- 条件: 1 つ目の把持のサブタスク（`grasp_subtask`、最大 200 ステップ）、500 エポック、UTD 5、`fixed_std` 0.02、3 環境。評価は D と同じ方式（シード 930000、50 エピソード）。比較: ベース（RLT 経路）0.46、D（把持の報酬 +1）0.62。
- A の設定: `online_bc_weight=1.0`、`sft_weight=1.0`、上位 30%、先読み 3 チャンク（30 ステップ）。B の設定: `reward_scale=2.5`。
- 環境の把持ゲート（局面の判定）と終了条件は、A・B とも、そのまま残っている（変えたのは、報酬と学習則だけ）。

### E0c（2026-10-05）: アンサンブル（5 メンバー）で、失敗エピソードの精度は上がるか — 結果: ほとんど変わらない
- `scripts/steam_rlt_hybrid/e0_ens.py`、結果 `tmp/hybrid/e0_ens_result.txt`。同じ分割で、シードだけ変えた 5 つの MLP。
- 失敗エピソードの前後の判定の正解率: 単体（5 つの平均）0.726 → 平均 0.728、最小 0.721（eval）。未使用の学習データでも 0.720 → 0.725 / 0.716。Spearman は +0.02 程度。
- 空振り vs 保持の AUROC（失敗エピソードのみ）: 単体 0.648 → 平均 0.654、最小 0.660。全体では 0.828 → 0.832 / 0.841。
- メンバー間のばらつき（標準偏差）: 成功 0.36〜0.43、失敗 2.83〜2.85（約 7 倍）。ばらつきと誤差の Spearman: 成功 0.43〜0.47、失敗 0.22〜0.23。→ 失敗エピソード（学習で見ていない領域）で、ばらつきが大きく、**不確実性の指標としては使える**が、精度の改善にはならない。
- 解釈: 失敗エピソードの低い正解率は、モデルの分散ではなく、(1) 学習で失敗を見ていない偏りと、(2) 失敗では、同じ場面の繰り返しや後退で、見た目から時間の前後が決まらない（正解自体が曖昧）ことが主因と考えられる。
- 含意: 案の「actor の信頼度」には、アンサンブルのばらつきが使える（E2 の候補として有望）。精度の改善には、失敗エピソードを学習に入れる（ただし、時間の前後ではなく、「進んでいない」ことを教師にする）などが必要。

### E0d（2026-10-05）: STEAM 論文の主張（最小値のアンサンブルが偽陽性を抑える）を、ラベルの偽陽性で確認 — 結果: この設定では、効果は小さい
- 論文の主張: 単一の予測器は、分布外（やり直し・後退）で過大評価し、偽陽性を出す。M 個の最小値で抑える（付録 E.4）。タオル折りで、M = 1 → 3 で、方策の成功率 72.7% → 92.3%、M = 5 は、さらなる改善なし（表 3）。
- 測定: 未使用エピソードで、各スコアの上位 30% を positive としたとき、失敗エピソードのフレームと、空振りのフレームのうち、positive になった割合（低いほうが良い）。`scripts/steam_rlt_hybrid/e0_ens2.py`、`tmp/hybrid/e0_ens2_result.txt`。
- 結果（失敗エピソードのフレーム / 空振りのフレーム / 成功エピソードのフレーム）: 単体（5 つの平均）0.117 / 0.058 / 0.737、平均 0.116 / 0.059 / 0.739、最小 0.111 / 0.051 / 0.750。メンバー間でラベルが食い違うフレームは 4.6%（失敗 5.2%、成功 3.3%）。
- 解釈: LIBERO の Task 0 では、単体でも、失敗エピソードのフレームが positive になる割合は、すでに低い（約 12%）。最小値で、さらに約 0.6 ポイント下がる程度。論文の効果は、実機の長い・多様なデータ（やり直し区間など）で大きく出ているとみられる。ここでは、確認できていない（同じ条件ではない）。
- 方針: アンサンブル（M = 3〜5、最小値）は、MLP なので、ほぼ無料。保険として採用する。ただし、大きな改善は期待しない。ばらつきは、信頼度の指標として使う（E0c）。
